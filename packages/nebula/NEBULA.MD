# Nebula Pulsar Cluster Management System

Nebula is a cluster management and coordination layer designed to extend Pulsar beyond individual engine deployments and allow multiple Pulsar instances to operate together as a unified distributed system.

Its primary purpose is to coordinate multiple Pulsar engine instances running across different serverless function deployments, edge environments, or persistent runtimes. Instead of requiring developers to manually distribute queues between separate Pulsar deployments, Nebula provides a centralized way to manage instances, distribute queue workloads, monitor their availability, and coordinate execution across the entire cluster.

Nebula acts as the control plane of Pulsar. It does not execute jobs or process messages itself. Instead, it manages the execution engines responsible for processing those jobs. Each Pulsar instance acts as a worker node, while Nebula maintains information about active instances, their assigned queues, execution capacity, and operational health.

When a Pulsar instance starts, it registers itself with Nebula using a unique instance identifier and reports its available execution capacity. Nebula then determines which queues should be assigned to that instance based on the current cluster topology and existing assignments. The instance receives its assigned workload and passes that configuration to the existing Pulsar engine, which continues handling message polling, scheduling, worker execution, and job processing as usual.

Nebula also manages queue ownership through a lease-based coordination system. A queue assigned to one instance is associated with an active lease, preventing multiple instances from independently claiming ownership of the same queue. Instances periodically update their heartbeat information to indicate that they are still operational. If an instance becomes unavailable or crashes, its heartbeat eventually expires. Nebula can then identify the instance as inactive, release its assigned queues, and make those queues available to other healthy instances in the cluster.

This allows Pulsar to recover from individual deployment failures without requiring developers to manually redistribute workloads. It also enables multiple deployments to share processing responsibilities and scale horizontally when additional execution capacity is available.

Nebula maintains its cluster topology and coordination state using a shared storage backend, such as Redis or PostgreSQL. This state contains information about registered instances, their health status, queue assignments, and active execution leases. Because the coordination state is shared, independently deployed Pulsar instances can communicate through the same cluster management system without requiring direct communication with one another.

Nebula is intended to be integrated into the Pulsar SDK as an optional cluster management module. Developers can enable it when initializing their Pulsar engine and provide an instance identifier and cluster configuration. When enabled, the engine communicates with Nebula during startup and throughout its execution lifecycle to obtain queue assignments, maintain its lease, and report its operational status. When the engine completes its execution cycle or terminates gracefully, it can notify Nebula so that its assignments can be released.

The deployment model allows developers to deploy multiple independent Pulsar instances across different environments while connecting them to the same Nebula cluster. For example, a developer could deploy one Pulsar instance on a Cloudflare Worker, another on a serverless function platform, and another inside a persistent container. All these instances could participate in the same cluster, with Nebula coordinating their queue assignments and availability through the shared Redis or PostgreSQL backend.

Nebula can also provide centralized cluster visibility and operational management. It maintains a unified view of registered instances, active queue assignments, execution health, and overall cluster activity. This creates the foundation for additional capabilities such as dynamic queue balancing, automatic workload redistribution, global cluster maintenance controls, graceful deployment upgrades, and automatic scaling based on queue backlogs.

In the broader Pulsar architecture, Nebula separates workload coordination from workload execution. Pulsar remains responsible for the actual messaging and job orchestration, while Nebula is responsible for deciding where and by which engine those workloads should be processed. Together, they allow Pulsar to evolve from an individual messaging and orchestration engine into a distributed system capable of coordinating multiple deployments as one unified processing cluster.
