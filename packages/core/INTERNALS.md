## HTTP_NETWORK_DRIVER - WEBSOCKET_NETWORK_DRIVER - CIRCUIT_BREAKER (25/10/26)

### ADDING CIRCUIT BREAKER FSM FOR PREVEANTING REPEATING FAILURE AND WASTING RESOURCES

THE PROBLEM WITH THE DISPATCH LAYER RIGHT NOW IS, IT DOESN'T KNOW WHAT TO DO WHEN THE DISPATCH FAILS.
AS THE WORKER DEREGISTRATION WAS SUPPOSED TO HEPPEN AT THE CONSUMER SIDE, WHEN THE CONSUMER ITSELF FAILS
THE ENGINE DOESN'T KNOW WHAT TO DO AND THE WORKER REGISTRY PILES UP WITH GHOST WORKER ID'S. RESULTING IN
A HAULT.

THE SOLUTION COULD BE IMPLEMENTED WITH 2 THINGS
    -  CIRCUIT BREAKER
    -  EXPONENTIAL BACKOFF

CIRCUIT BREAKER HERE IS REFEREING TO A FSM STATE THAT WILL CHANGE ITS STATE DEPENDING ON THE CONDITION.
    AS CONSECUTIVE DISPATCH FAILS IT WILL INCREAMENT THE NUMBER AND WHEN IT REACHES ITS THREASHOLD EX : 10
    THE STATE WILL TRANSITION TO OPEN, WHICH WILL BLOCK ANY FURTHER TICK EXECUTION FOR THAT SPECIFC QUEUE.

    AS FOR BLOCKING `TICK EXECUTION`
        IT MEANS
            - NO MORE DB CALL'S
            - NO MORE REDIS(IF ENABLED) COMMAND'S

        BASICALY TO PREAVENT THE TICK CONTROLER FROM RUNNING THE TICK SERVICE AT ALL. 
            SIMILER TO HOW IN PERSISTENT RUNTIME WHEN THERE IS NO CONNECTED WORKER THE TICK CONTROLLER DONT GET THE 
            PERMISSION TO START THE TICK PROCESS.
    
    WHEN THE STATE TRANSITION FROM CLOSE -> OPEN, IT WILL ALSO GOING TO SET A 'next_open_at' TIME IN STORAGE LAYER,
    THEN DEPENDING ON RUNTIME THE IMPLEMENTION WILL DIFFER, HOWEVER THE MAIN GOAL IS TO TRACK DOWN IF THE 'next_open_at'
    IS RIGHT NOW OR LATER.
    WHEN THE TIME COMES, THE ENGINE WILL TRANSITION THE CIRCUIT BREAKER STATE FROM OPEN -> HALF-OPEN, DURING THIS STATE
    IT WILL SEND 1 REQUEST/EVENT TO THE CONSUMER SIDE, THIS TIME IN A DIFFERENT ROUTE/CHANNEL FOR HEALTHCHECK AND STATUS.
        - IF RETURNED WITH 200 FOR HTTP OR OK/TRUE FOR SOCKET > THE STATE WILL TRANSITION TO CLOSE.
        - IF RETURNED NOT 200 FOR HTTP OR NULL/UNDEFINED/EXCEPTION/FALSAE FOR SOCKET > THE STATE WILL TRANSITION BACK TO OPEN,
            AND WILL CREATE A NEW 'next_open_at'.
    
    AND THIS WOULD LOOP.

    AS FOR EXPONENTIAL BACKOFF
        WHEN THE FIRST FEW REQUEST/EVENTS FAILS THE CONCURRENCY LEVEL DISPATCH WOULD STOP AND IT MAY START SENDING REQUEST IN SEQUENTIAL WAY
        BY DOING THAT TRACKING EACH REQUEST/EVENT WOULD BECOME EASIER, THEREFOR WHEN THE FIRST FAILS THE NEXT DISPATCH WOULD HEPPEN EXPONENTIALY
        INSADTE OF THE SAME PACE AS THE PREVIOUS ONE

    COMBINING BOTH CIRCUIT BREAKER APPROACH WITH EXPONENTIAL BACKOFF WE CAN PREAVENT EXCESSIVE RESOURSE USAGE AND FAILED LATENCY, ENGINE HAULT

## QUEUE - PULSAR

### INTERVENTION POLICY
    THE `INTERVENTION POLICY` IS CURRENTLY NOT COMPLETED BUT THE IDEA IS PRETTY SIMPLE. IN TRADITIONAL MESSEGING QUEUE ONCE THE JOBS ARRIVE THE CONSUMERS
    START PROCESSING THOSE JOBS THERE IS STOP BUTTON THAT WILL PAUASE/RESUME THE DISPATCH PART.
    THE INTERVENTION MECHANISM WOULD ALLOW PULSAR TO ACCEPT OUTBOUND SIGNAL TO INTERVENE IN THE TICK PROCESS TO RESUME/PAUSE THE EXECUTION.

    A BASIC EXAMPLE WOULD BE
        PDF_QUEUE HAS 10_000 JOBS.
        THE CONSUMERS ARE ACTIVLY PROCESSING PDF.
        PULSAR IS RUNNING.

        NOW FOR SOME REASON LETS SAY FAKE PDF OR CORRUPT PDF DATA HAVE INSERTED INTO THE PGMQ BUT THE PULSAR IS RUNNING AND DISPATCHING THOSE JOBS TO THE CONSUMERS.
        
        THE CONSUMERS ARE RECIVING CORRUPT DATA.
        
        NOW HOW TO STOP THIS.
            - ONE IS TO PURGE THE PGMQ
            - REDEPLOY PULSAR SO ITS STATE AND EVERYTHING GET RESET
            - SOMETHING ELSE

        FOR THIS REASON THE 'INTERVENTION MECHANISM WAS INTRODUCED'
            WITH 'INTERVENTION' A SIMPLE HTTP REQUEST IS ENOUGH TO STOP THE TICK PROCESS FOR THAT PERTICULER QUEUE OR PAUSE ALL QUEUES TICK PROCESS.
                SO IN PRACTICE IT WILL LOOK SOMETHING LIKE
                    CONSUMER GETTING CORRUPT DATA, HAVE TO STOP THIS
                    (ASSUMING PULSAR IS DEPLOYED IN A SERVERLESS/EDGE RUNTIME) WE WILL SEND A SIMPLE HTTP POST REQUEST TO THE ENDPOINT, 
                    `DEPLOYED_FUNCTION_URL/pause`. IN THE HEADERS IT WILL ACCEPT DATA SUCH AS
                        - `queue` : string > TARGET QUEUE NAME OR '*' TO PAUSE ALL QUEUE

            ITS BASICALY TO MAKE STOPING EASIER.

        CURRENTLY THE 'INTERVENTION MECHANISM' DOES NOTHING AS IT WILL BE DETERMINED IN THE FUTURE BASED ON FEEDBACK AND OTHER SENIOR PEOPLE ADVICE WETHER
